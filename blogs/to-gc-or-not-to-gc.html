To GC or not to GC

Nobody has ever given me a compelling reason why the software industry has embraced languages that do not require engineers to free memory once an object goes out of scope, other than ‘developer velocity’. We traded memory safety for the ability to pretend that RAM is an infinite, free resource. As AI improves, I hope that, eventually, everyone will write code in Rust, if not C or C++.

If you’re among the vast majority that enjoys coding in the JVM, you should understand what happens to memory. The garbage collector (GC) clears allocated memory at runtime. Traditional GCs like G1GC and Parallel are basically hoarders with anxiety-they refuse to throw away a single byte of memory until they’re 100% sure your code won't come crawling back for it. Newer algorithms, like ZGC, are more optimistic, sure, but at the end of the day, they’re still just an expensive room-cleaning service for the mess your code shouldn't have made in the first place.

In two isolated servers running the same code—one on the JVM and one in Rust—the JVM server used a maximum of ~2.5 GB of memory, while the Rust server used ~100 MB for the same handler. As RAM becomes scarcer and more expensive, I wonder how long it will take software companies to realize how much memory they could save by simply asking AI to rewrite their code in a more performant language.

While building a system written in a language that uses GC, I believe it is imperative to also spend time in reasoning how strong of a GC trigger one needs. Though GC algorithms are mostly treated as black boxes, there are ways to tweak its frequency in order to adjust the heap memory more to your liking. In JVM there are hundreds of -Xms / -Xmx flags that allow tweaking of ‘when’ a GC event should be triggered. For example, you could lower your max heap memory by triggering GC events at a lower heap occupancy threshold, or switching to a better GC algorithm, or perhaps even writing System.gc() calls after literally every function in code (hehe).

Increasing the frequency/thresholds of your GC triggers would also help smoothen out some of the CPU spikes that you observe during the execution of your service (provide the incoming QPS remained the same). The spikes for a JVM service would, most likely, be due to a big ‘stop-the-world’ GC pause, especially if you’re running an old GC algorithm (like G1GC/ParallelGC). If done correctly, it could also prevent a few alerts that you dismiss as being ‘intermittent issues’.

The tradeoff you would have to consider here is that triggering GC at a higher frequency would cause a small bump in the average CPU utilization. In my opinion, the improvements in memory should outweigh the bump in CPU utilization. While experimenting further with the same JVM server (mentioned earlier), explicitly recommending the system to trigger GC every 2 minutes (via System.gc() calls), saw a 5% increase in CPU utililzation while the max heap usage dropped from ~2.5GB to ~600MB.

As AI removes more and more coding bottlenecks, and system design becomes the ‘new coding’, I really hope that memory management is given higher importance than what it receives today. While designing modern systems, most people focus and argue over kafka partitions and db indexes, yet completely ignore the fact that application node themselves are drowning in RAM bloat. If we treat database indexing as some sacred art, why hasn’t tuning language runtime become the most common spell in the book?
